Network diagnostics

Which connection stage or protocol failed?

Stable · v0.7.0
  • 13 bounded diagnostic modes
  • Protocol-native evidence
  • Offline subnet planning

Published v0.7.0 includes Network → Diagnostics at /network/diagnostics. Choose a question, enter one target and run it explicitly. The page makes no network requests on opening or changing modes. Results and private inputs live in this tab's memory.

These 13 modes answer connection questions; they are separate from the HTTP/gRPC/WebSocket/SSE/ Cap’n Proto workbenches, TCP port scanning and capture-file reading. HTTP/2 and HTTP/3 diagnostics perform the limited exchanges described below, not arbitrary application requests or packet decryption.

The local CLI enables this capability only in safe local mode. Each request requires CSRF validation and a direct loopback peer; forwarded and remote requests are refused. Embedded handlers omit probes by default and must explicitly select standalone.WithNetworkDiagnostics(). The unsafe remote CLI mode does not enable them.

Search commands with Ctrl/Cmd+K or link to a mode using, for example, #/network/diagnostics?mode=dns-compare&target=example.com. Opening a link only prepares a draft.

Bounds and interpretation

An operation lasts at most 15 seconds; each probe uses 0.1–3 seconds. Connection sampling accepts 1–20 attempts with a 0–1 second interval. Two diagnostics can run at once. Resolution admits at most four addresses per family; larger answers require an explicit IP rather than silently dropping destinations. Unspecified, multicast, reserved and known local directed broadcast addresses are rejected. Explicit IPv6 zone identifiers are retained.

Default DNS uses ProtoPeek's OS/Go resolver path. It does not promise the browser's resolver, NSS behavior, cache state or split-DNS selection. The system API does not expose raw TTLs, response codes or SOA. An explicit DNS server must be a unicast IP, with optional port; replies must match the ID and question. Truncated UDP replies use bounded TCP fallback.

TCP connectivity is not HTTP or RPC health. Proxy acceptance is the proxy's claim that a tunnel was established, not an application response. Proxy DNS is not tested: ProtoPeek resolves the destination locally. HTTP/3 shows the actual status independently from transport success. It sends HEAD / even when the input URL contains a path.

IPv4 /31 uses point-to-point semantics and /32 contains one address. IPv6 counts all addresses without claiming they are allocated hosts. Only an RFC1918 IPv4 /24 or smaller can prepare a nearby-device scan. That handoff opens the existing plan; Scan network is still a separate explicit action.

Private inputs and exported evidence

Private CA PEM augments trust only for that run. It is never installed, persisted or exported. Certificate verification remains enabled. Received chains and verified chains are separate, so a missing intermediate or unknown root remains visible.

Proxy usernames/passwords remain in memory. These proxy handshakes use plaintext to the proxy; the page warns before use. Server responses cannot reflect arbitrary proxy text or headers into errors or reports. API request/response bodies are excluded from verbose CLI dumps.

Raw sent payloads are excluded from results. Replies remain visible only on this screen and are omitted from Export evidence, since a service can echo a private request. Exported diagnostic metadata can still identify private hosts and certificates; review it before sharing. Session activity stores only a closed outcome, elapsed time and counts, not diagnostic payloads, credentials, CA input or free-form errors. The new raw diagnostics are not agent/MCP tools.

Verification

The package uses real loopback TCP, UDP, DNS, proxy, TLS, HTTP/2 and HTTP/3 fixtures, including untrusted/private CA, refusal, cancellation and bounded input tests. Browser acceptance uses the native Windows server and local protocol peers. Native Linux/macOS and release packaging remain distinct CI gates; a successful web build alone is not native runtime evidence.
